# Noosphere AI 应用与 Agent 开发实习学习方案

适用对象：刚开始借助 AI 学编程，希望通过 Noosphere 项目申请 AI 应用或 Agent 开发实习的大学生。

学习投入：每周 10–15 小时。建议主线 16 周，共 160–240 小时；基础练习未通过时顺延，允许用 20–24 周完成。16 周是安排任务的参考，不是获得实习或精通所有技术的保证。

编写日期：2026 年 10 月 12 日。项目依据为本机 `E:\project\Noosphere（agent项目）\new` 下的当前源码、9 月架构说明，以及截至 10 月 11 日的工作区、项目知识、Agent 和操作审批文档。

这份方案的目标，是让你逐渐做到：**看懂一条完整功能链路，独立实现一个小功能，用测试证明它有效，并向面试官说明你为什么这样做。** 项目涉及的语言很多，但学习可以分批完成。

本文已对照架构文档和关键实现；没有重新执行整个项目的测试或发布验收。历史验证记录中的通过数量、性能数据，不代表你已经亲自完成这些工作，也不能直接变成你的个人成绩。

## 先从这里开始

第一次只读本节、第一章和第五章的第 1 周。其他章节按学习进度使用，不需要今天全部看完。

建议把你要达到的状态分成三层：

1. **会使用、会说明。** 能启动程序，演示聊天、项目检索和 Agent，知道每个模块解决什么问题。
2. **会阅读、会定位。** 能从按钮找到请求入口，再找到业务实现；出错时能判断应该查哪一层。
3. **会修改、会证明。** 能自己拆解需求、写核心逻辑、补测试、记录结果，并解释改动的取舍。

第 1 层是起点，第 3 层才是这份方案最终要积累的实习竞争力。你可以继续用 AI，但是关键逻辑必须达到“关掉 AI 后仍能复述，换个相似需求仍能自己动手”的程度。

全文阅读顺序：

## 一 你在做一个什么项目

你可以先这样理解 Noosphere：

> 这是一个运行在 Windows 上的 AI 桌面工作台。用户选定代码项目后，可以与模型对话、检索项目代码和已确认的项目知识，让 Agent 使用受限制的工具检查问题，并在人工确认后执行部分操作。

“本地桌面”表示界面、本地服务和主要项目数据在电脑上运行；如果选择远程模型或远程向量服务，相关请求与上下文会发送给服务提供方。它不天然等于完全离线。

### 1.1 用一个问题串起整个系统

假设用户问：“这个项目从哪里启动？帮我找代码，再提出一处说明文字的修改。”

系统不能只生成一段听起来合理的回答。它需要知道当前项目是什么，找到启动代码，读取真实内容，留下文件位置和版本证据，再把修改建议展示给用户。只有用户确认后，操作执行层才可以修改文件。

这就是你学习时始终要抓住的主线：**输入目标 → 找资料 → 调工具 → 记录证据 → 给出答案或提案 → 人工确认 → 检查结果。**

### 1.2 整体架构的白话解释

```text
用户点击与输入
      ↓
React + TypeScript             画界面、显示状态、接收操作
      ↓ Tauri IPC              IPC 就是程序内部不同部分传递消息
Tauri + Rust                   管窗口、转发请求、管理本地后端进程
      ↓ 本机 HTTP
Go 统一后端                    组织业务、校验权限、管理任务
      ├─ Gateway               和不同模型提供方通信
      ├─ CodeLens 适配器 → Python + Tree-sitter
      │                        解析源码结构并建立代码片段
      ├─ Nebula + knowledge    保存和检索代码、管理已确认知识
      ├─ agent                 工具循环、操作提案、执行与恢复
      ├─ workspaces            项目绑定、任务、事件、重启状态
      └─ DevOps                系统状态与运维工具
```

你第一次看到这个图，只需要记住一句话：**前端负责让人操作，后端负责把事情做对；桌面层负责把它们组织成一个应用。** 后续再逐渐理解每条箭头。

### 1.3 不同内容保存在哪里

| 内容 | 当前主要存放方式 | 为什么要区分 |
|---|---|---|
| 聊天会话正文 | 前端 IndexedDB | 聊天消息的保存与恢复有自己的流程 |
| 工作区、后台任务、任务事件和结果 | 后端 SQLite，使用 WAL 模式 | 页面关闭后仍可查询任务；重启后保留状态 |
| 代码片段、记忆记录及检索数据 | Nebula 的存储和索引体系 | 需要按项目检索，并核对来源版本 |
| 操作提案、原文和执行状态 | 数据目录下 `agent-actions` 的本地日志 | 用于审批、冲突检查和恢复 |
| 模型与运行配置 | 对应数据目录的配置文件 | 与源码和分发模板分开管理 |

SQLite 的 WAL 模式与 Nebula 自己的 WAL，都使用“先记录写入”的思路，但属于两个不同系统，不是同一份日志。

不要把“聊天历史”“长期记忆”“任务记录”混为一谈。聊天里出现过一句话，不代表它已经被核实并成为长期知识。

## 二 优化后项目最值得学习的能力

### 2.1 优化解决了什么真实问题

| 原本容易遇到的问题 | 当前设计思路 | 你能学到的能力 |
|---|---|---|
| 每个页面自己查询后端，重复请求 | 全局 BackendProvider 共享后端状态 | 状态所有权、避免重复工作 |
| 首次打开就加载所有页面和场景 | 页面与三维场景按需加载 | 区分必要工作和可延后工作 |
| 点停止只让界面停止显示，后台仍继续 | 将取消传到请求、任务和工具执行边界 | 生命周期、超时与取消 |
| 多项目数据混在一起 | 工作区绑定项目，按作用域检索并复核 | 数据隔离、身份一致性 |
| 代码修改后仍把旧片段交给模型 | 使用源码哈希和来源版本验证 | 数据新鲜度、可信引用 |
| 每次索引都重新做所有计算 | 复用未变文件的解析结果和未变片段向量 | 增量处理、区分内容与元数据 |
| 模型说自己执行了，但没有证据 | 工具结果、调用 ID、步骤与证据留存 | 可检查的 Agent 执行流程 |
| 模型建议修改后直接执行 | 保存提案，人工逐项确认，再执行 | 人与模型之间的权限分工 |
| 恢复覆盖了用户后来的修改 | 执行和恢复前检查对应版本的哈希 | 冲突检测、有条件恢复 |
| 程序重启后不知道任务进行到哪了 | 保存任务状态，将未完成任务标为中断 | 持久化、重启恢复、避免重复执行 |

学习时先问“如果不这样做，会出什么问题”，再看代码。这样比背技术名称容易记住，也更接近面试中的讨论方式。

### 2.2 需要按最新实现理解的边界

以下内容不是缺点清单，而是你介绍项目时需要准确表达的范围。

- **旧架构说明不是最新功能清单。** 9 月 Word 文档还把取消等内容列为后续工作；当前学习要结合 10 月专项文档。旧的固定行数切块说明，也不能替代当前的符号级切分说明。
- **真实语义向量与哈希向量不同。** 未配置真实 embedding 时，项目明确使用“关键词与哈希向量检索”。不能因为接入聊天模型，就说已接入语义 embedding。
- **项目作用域内的向量搜索采用限定范围后的精确评分。** 代码有名为 HNSW 的图索引实现，但不能由文件名推出“所有搜索都走完整分层 HNSW”或“已验证大规模近似搜索性能”。
- **当前增量优化有范围。** 未变数据可以跳过部分工作；向量内容变化时仍会重建全图并切换。不能描述为完全增量维护 HNSW 边。
- **调用关系是保守静态分析。** 能确定的关系记录下来，无法确定的动态调用或跨文件关系保留为未解析。它不是完整编译器语义分析。
- **聊天支持的提供方与 Agent 工具调用支持范围不同。** 当前工具能力校验接受 DeepSeek、OpenAI、OpenAI 兼容和 Ollama 配置，具体端点与模型还要支持工具协议。
- **提案、执行成功、恢复成功是不同状态。** 恢复需要版本匹配；测试进程产生的外部副作用没有自动回滚保证；多文件操作不是一个原子事务。
- **历史测试证明的是对应环境下的行为。** 模拟模型可以验证工具协议和失败处理，不能替代真实模型质量评估。浏览器中的模拟桌面接口测试，也不能替代最终原生窗口的完整验收。

这些区别会成为你后期很有价值的面试材料。能指出设计的适用范围，说明你理解实现，而不是只记住宣传用语。

你暂时不需要从训练大模型、CUDA、复杂分布式系统或从零写数据库开始。先把一个小型应用做正确，再按岗位要求补充。

### 3.2 常见词的第一遍解释

| 词语 | 初学时可以这样理解 |
|---|---|
| API | 一个模块给另一个模块使用的明确入口 |
| HTTP | 客户端和服务端交换请求、响应的规则 |
| JSON | 用文字表示列表、对象、数字等数据的格式 |
| Token | 模型处理文本时使用的单位，不总等于一个字或单词 |
| 上下文 | 这一次请求实际交给模型的资料 |
| Embedding | 把内容转换为数值向量，用来比较相似性；效果取决于具体方法 |
| RAG | 先检索相关资料，再让模型参考资料回答 |
| BM25 | 根据查询词与文档中词语的匹配情况进行排名 |
| RRF | 根据多个结果列表中的名次合并排名 |
| AST | 把源码解析成有层次的结构，例如函数、类、调用表达式 |
| Tool Calling | 模型提出结构化工具请求，应用校验并执行，再返回结果 |
| Agent Loop | 模型决定下一步，应用执行工具，模型再根据结果继续 |
| Hash | 内容的数字指纹，用来检查内容是否变化 |
| Revision | 一条记录的版本号，帮助发现别人先修改过的情况 |
| 状态机 | 明确“当前是什么状态、下一步允许进入什么状态” |
| 幂等 | 重复请求不会产生额外业务效果；本项目重复审批采用拒绝再次执行 |
| Mock | 测试替身，模拟外部服务的返回，便于稳定验证程序行为 |

第一遍能把词和具体例子联系起来就够了，不要求背定义。

## 四 每周怎样学才有效

### 4.1 以 12 小时为例安排一周

| 活动 | 时间 | 实际做什么 |
|---|---:|---|
| 学一组必要概念 | 2 小时 | 阅读指定小节，自己写几个例子 |
| 阅读对应源码 | 2 小时 | 跟踪一条链路，记录输入、处理、输出 |
| 独立练习与调试 | 4 小时 | 做小实验、运行、改错、验证边界 |
| 编程与计算机基础 | 2 小时 | 字符串、字典、简单算法、HTTP 或 SQL |
| 复述与证据整理 | 2 小时 | 做小测、保存结果、录 3 分钟讲解 |

只有 10 小时时，先缩减选学内容，不删掉独立练习。达到 15 小时时，把额外时间用于复习卡点和扩展测试，不再同时开一门新课。

### 4.2 每次 90 分钟的固定流程

1. 10 分钟：不看资料，回忆上次学了什么。
2. 20 分钟：只学习今天任务需要的一个概念。
3. 40 分钟：写代码或跟踪源码，自己运行并处理错误。
4. 15 分钟：检查正常、异常或边界情况。
5. 5 分钟：记下今天能独立完成什么，以及下次从哪里继续。

### 4.3 AI 的用法从代写逐步转向辅导

可以让 AI 解释陌生语法、帮你定位文件、生成练习题、审查你写的代码。核心练习先自己写，遇到问题先提供你的推理和实际错误，再请求一个提示。

推荐使用这样的提示词：

> 我是编程初学者。请用一个具体例子解释这个函数，先说输入和输出，再说关键步骤。遇到新术语先解释。不要一次介绍整套框架，最后出两道小题让我确认理解。

> 这是我自己写的代码、期望结果和实际错误。请先检查我的思路，只给一个最关键的提示，让我自己修改。修改后再帮我检查边界情况。

> 请当面试官，一次只问一个问题，从我这次实际改动开始。追问为什么这样设计、失败怎么办、怎么验证。不要替我编造项目成果。

每周至少安排一次 30–45 分钟独立小测：允许查语言文档，暂停 AI 生成和代码补全，从空文件完成练习。这样测的是你能否组织代码，不是能否记住所有语法。

### 4.4 什么时候可以进入下一阶段

- 第 4 周门槛：能自己写读取文件、输出 JSON、处理错误的小程序，并解释一次 HTTP 请求。
- 第 8 周门槛：能跟踪聊天和代码索引链路，读懂对应 Go/Python 函数，解释取消与增量复用。
- 第 12 周门槛：能写一个简化工具循环，说明来源验证、预算和审批为什么存在。
- 第 16 周门槛：有本人完成的实践、可复现的测试或评估、真实简历和项目演示。

某道门槛过不了，就用下一周重复小练习并整体顺延。不要用继续看更难的教程替代当前缺失的动手能力。

### 第 1 周 认识项目和开发工具

**本周问题：我点开一个程序后，到底有哪些东西在工作？**

先理解文件、文件夹、绝对路径、终端、命令、进程、端口、依赖。终端只是用文字操作电脑的入口；报错是程序告诉你哪一步没有满足条件。

阅读 `README.md`、`docs/DEVELOPMENT.md` 和本文架构图。尝试使用现有启动器打开项目，找到聊天、CodeLens、Nebula、DevOps 与工作区入口。没有配置模型时，先观察界面和已有记录，不要求为了第一周完成付费调用。

本次查看的 `new` 目录没有 Git 元数据。先在独立练习目录学习 `git init`、`git status`、`git diff`、`git add`、`git commit` 和 `git log`。以后为项目建立真实版本历史时，只记录今后的实际改动；不要伪造以前的提交，也不要把模型密钥、运行数据和发布产物整包提交。

**本周行动：**

1. 运行只读环境预检，记录缺哪个工具、应该去哪里检查。
2. 启动程序，截图标注五个主要入口。
3. 用纸或 Markdown 画一张“界面 → 桌面桥接 → 后端 → 模型或 Python”的图。
4. 在练习目录创建一个文字文件，修改两次，用 Git 看差异并提交。

**验收：**不看图，用 2 分钟说明 frontend、backend、desktop、release 的区别。解释为什么手改 release 中的文件不是正常开发方式。

**第 1 周逐日建议：**第 1 天认识目录，第 2 天运行和记录，第 3 天学习终端，第 4 天学习 Git，第 5 天画图，第 6 天复述与补缺，第 7 天休息或做 20 分钟回顾。每天 60–90 分钟，周末另留 2–3 小时集中练习。

### 第 2 周 用 Python 建立编程基本功

**本周问题：我能否把一个小需求拆成输入、步骤和输出？**

学习变量、字符串、数字、列表、字典、条件、循环和函数。先不学装饰器、元类或复杂面向对象。

写一个小脚本，统计练习目录中 `.py`、`.go`、`.ts` 文件的数量。第一版只统计一个目录；完成后再加子目录扫描和忽略规则。这个练习对应 CodeLens 的“找到需要处理的文件”，但不需要照抄现有大文件。

**验收：**从空文件重写核心统计逻辑；能解释字典为什么适合存“扩展名 → 数量”。给程序一个空目录，它应该返回空结果或零计数，而不是崩溃。

**交付：**脚本、3 组输入输出、100 字左右的思路说明。

### 第 3 周 文件 JSON 异常和测试

**本周问题：输入不符合预期时，程序怎样可靠地告诉我？**

学习 `pathlib`、UTF-8、`json`、`try/except`、模块导入、虚拟环境和 `unittest`。理解“函数返回错误信息”和“把错误悄悄吞掉”的区别。

把第 2 周脚本升级成文件摘要工具：输入一个练习项目目录，输出文件路径、类型、字节数和行数，并保存 JSON。行数与字节数是不同量，含中文的文件尤其能帮助你理解编码。

**验收：**测试正常目录、空目录、目录不存在、含中文内容、忽略目录五类情况。自己故意改错一个判断，观察测试变红，再恢复。不要为了让测试变绿而删除断言。

**交付：**一个可重复运行的小工具、一份测试结果、一个真实错误及修复过程。

### 第 4 周 HTTP 和第一个小接口

**本周问题：为什么界面与后端可以分开写？**

学习客户端、服务端、URL、GET、POST、请求头、JSON 请求体和常见状态码。结合项目理解 401 表示认证未通过，409 表示版本等状态冲突，而不是简单归为“程序坏了”。

使用 FastAPI 包装前面的小工具。为了控制范围，只让接口读取你预先指定的练习目录，暂时不提供任意路径参数。做一个健康接口和一个按相对文件名查询摘要的接口，再写 Python 调用脚本。先使用固定数据与本地响应，不依赖模型。

阅读 `backend/python/codelens/main.py` 的接口定义部分，找出“接收参数 → 调用函数 → 返回数据”的结构；暂不逐行研究整个服务。

**验收：**能解释一次请求里的方法、路径、参数和响应；输入不存在的文件时能得到明确错误。通过第一个阶段门槛后，整理一段 3 分钟演示。

### 第 5 周 读懂 Go 后端

**本周问题：我的 Python 知识如何迁移到 Go？**

学习 Go 的变量、函数、struct、slice、map、error 和最基础的 interface。把 Python 字典与 Go map、Python 的对象数据与 Go struct 对照起来理解。指针先理解“可以引用同一个值”，无需一开始钻研全部内存细节。

阅读 `backend/cmd/server/main.go` 的装配流程、`router.go` 的健康接口，再选择一个简单 Gateway handler。注意有些新模块在自己的注册函数里挂路由，不能把旧路由注释当成全部接口清单。

**动手：**在独立 Go 练习目录实现一个返回 JSON 的健康接口，并写一个输入校验函数和对应测试。

**验收：**能回答“main 为什么不应该包含所有业务”“HTTP handler 与业务函数有什么不同”“为什么 Go 经常返回 value 和 error”。

### 第 6 周 Gateway 流式响应与取消

**本周问题：聊天为什么可以边生成边显示，点停止后谁负责停止？**

学习消息列表、模型配置、流式响应、SSE、超时和 `context.Context`。先把 context 理解为沿调用链传递的“取消与截止时间通知”，再看具体 API。

按 `chat-runtime.ts → api.ts → gateway.rs → Go Gateway` 的顺序找调用点。前端使用 Tauri Channel 接收事件；后端与模型之间的流式协议经过桥接，不能把整条链路都叫作浏览器直连 SSE。

**动手：**在练习程序中每隔一小段时间返回一个片段，加入取消信号。观察正常结束、执行中取消和服务端错误。慢响应可以用本地模拟器制造，不需要反复调用付费模型。

**验收：**能解释“界面停止追加文字”与“后台请求真的取消”的区别；能指出取消应在哪些边界检查。知道普通调用的重试策略不能直接套给 Agent——当前 Agent 工具轮次没有隐式模型重试。

### 第 7 周 只学够用的前端

**本周问题：为什么切换页面后，旧请求不能把结果写到新会话？**

先学 JavaScript/TypeScript 的对象、数组、类型、Promise 与 async/await，再学 React 组件、props、state、事件和最基本的 effect 清理。不要求重写主页。

阅读 `ChatInput.tsx`、`chat-runtime.ts` 中发送入口，以及 `stream-runner.ts` 的身份和状态处理。理解 requestId、sessionId、workspaceId、projectId 各自解决的归属问题。

**动手：**在小型练习页面做输入、发送、加载、成功、失败、取消六种状态，模拟一个慢请求。请求完成前换一个对象，验证迟到结果不会写错地方。

**验收：**能解释组件临时状态、聊天持久化状态、全局后端状态的区别；能说明 BackendProvider 统一轮询为什么减少重复工作。对 IndexedDB 先掌握保存与恢复用途，不钻研全部 API。

### 第 8 周 CodeLens 与增量索引

**本周问题：一堆源码文件怎样变成可以引用的知识片段？**

学习函数、类、语法树、符号、相对路径、行号、文件哈希和缓存。阅读 `project_index.py` 的 `build_index` 主流程，再看 `symbol_chunks.py`；`ast_parser.py` 先按需查看调用到的部分。

**动手：**创建一个只含 3–5 个文件的小项目，做四组实验：首次索引；完全不改再次索引；只在函数前插入注释；修改一个函数正文。记录哪些文件被重新解析、哪些片段内容改变、哪些只是位置元数据变化。

缓存是“之前的计算结果”，哈希是“判断内容是否相同的指纹”。进程内解析缓存重启后会消失，但磁盘上的内容和向量仍可能复用，要分开观察。

**验收：**用具体例子解释符号切分比固定行数切分的好处与局限。说明为什么行号变化不应必然使未变函数重新计算向量，以及为什么当前实现不能叫作完整语义分析。

### 第 9 周 检索 RAG 和向量

**本周问题：找到相关资料与生成正确答案，是不是同一件事？**

学习关键词检索、向量相似性、top-k、BM25、RRF 和上下文预算。先用 10 段你能完全读懂的文本做实验，之后再换成代码片段。

阅读 `engine.go` 的 `SearchScopedContext`、`retrieval/hybrid.go` 的 `RRF`，再看向量搜索的项目作用域分支。先理解排序与融合，不要求推导 BM25 全公式或重写图索引。

**动手：**写一个简单关键词检索器，再写一个合并两份排名的 RRF 函数。项目中的基本形式为：每份列表中名次越靠前，贡献的 `1 / (k + 名次)` 越大；多份列表的贡献相加。这个名次从 1 开始。

比较“函数原名查询”“换一种说法查询”“项目里不存在的内容”。如果使用哈希向量，只报告该模式下的结果；如要研究语义召回，单独配置真实 embedding 并记录服务与模型，预算不足可推迟。

**验收：**说明检索没找到、检索找到但来源过期、模型没遵循来源，是三种不同失败。不要因为答案有引用编号，就认为所有陈述都已经被证据支持。

### 第 10 周 长期记忆与可信来源

**本周问题：怎样避免把模型的猜测保存成下次回答的事实？**

学习 proposed、confirmed、rejected、superseded，分别表示待确认、已确认、拒绝和已被替代。阅读 `knowledge/service.go` 中保存、来源失效和上下文准备的函数。

理解 revision 的例子：两个人都读到版本 3，第一个人保存成版本 4，第二个人还拿版本 3 保存时，应先报告冲突，而不是覆盖版本 4。

**动手：**用临时工作区验证待确认记忆不进入上下文、确认后进入、修改来源文件后排除、切换项目后不串用、旧版本更新返回冲突。当前功能已经存在；你的任务是理解并验证，而不是把它重新命名成新增成果。

**验收：**能讲清“项目相关”为什么不足以代表“当前可信”，以及为什么检索失败时普通聊天仍可继续，但应显示没有使用项目依据。

### 第 11 周 写一个最小 Agent

**本周问题：Agent 比单次模型问答多了哪几步？**

阅读 `agent/run.go`、`registry.go` 和 `gateway/tools.go`。把实现拆成：提交消息、获得结构化工具调用、校验工具和参数、执行、记录结果、使用相同 tool_call_id 回传、进入下一轮。

本周的 Python 练习只提供 `list_files` 和 `read_file`，根目录固定为你的练习项目；默认使用你写的模拟模型返回工具请求，再返回答案。预算可以设置为更小的 3 轮模型、4 次工具，便于测试。

```text
收到目标
重复执行，直到达到预算：
    检查是否已取消
    获取模型响应
    如果响应是最终答案，结束
    验证工具名、参数、路径、调用 ID
    执行允许的工具
    保存真实结果，并把结果交回模型
达到预算后，明确说明停止原因
```

这是一段理解用的流程，不是可以直接复制执行的完整程序。

**验收：**未知工具被拒绝；越出根目录的路径被拒绝；重复调用达到限制后停止；取消后迟到工具请求不执行；模型说“成功”不能替代工具执行结果。随后解释 Noosphere 的 6 次模型请求、12 次工具调用、120 秒总时限与 15 秒工具时限分别限制什么。

### 第 12 周 操作提案 审批与恢复

**本周问题：怎么允许 AI 帮忙改文件，同时让每一步都可以检查？**

阅读 `agent/actions.go`、`action_http.go`，以及 `AgentActions.tsx` 中的确认入口。先跟文件操作，再了解固定测试和服务操作。

**动手：**在自己创建的临时文件上完成：读原文 → 提出唯一匹配替换 → 保存修改前后内容及哈希 → 展示预览 → 用户确认 → 检查原哈希 → 写入 → 记录结果。然后加入“只有当前内容仍等于本次写入版本才恢复”的判断。

依次验证：提案阶段文件不变；批准后改变；重复批准不再执行；你在外部修改文件后，恢复应拒绝覆盖；状态匹配时能恢复原文。

**验收：**说明为什么模型不能批准自己的操作，为什么固定测试命令不等于运行了一个隔离沙箱，为什么取消测试不意味着撤销测试已经产生的所有副作用。服务功能本周只阅读和用模拟状态练习。

### 第 13 周 任务持久化与独立实践

**本周问题：页面消失或程序重启后，任务应该变成什么状态？**

用约 3 小时阅读 `workspaces/manager.go` 与重启测试，学习 SELECT、INSERT、UPDATE、主键、事务和基本任务状态。画出 queued → running → completed/failed/cancelled 的路径，并补充重启后的 interrupted。区分“页面切换”与“退出后端进程”。

剩余时间开始第七章推荐的独立实践：检索与来源有效性评估工具。它主要使用 Python，不要求同时重写任务调度器。

**验收：**可以解释为什么后台任务不应该只存在于 React state，为什么重启后不自动重放有副作用的操作。独立实践至少完成固定样本读取、结果保存和一个可检查的指标计算。

### 第 14 周 评估与失败分析

**本周问题：我说“改好了”，别人拿什么判断？**

完成第七、八章的小型评估。保持同一份项目快照、同一批问题、相同 top-k 和运行模式，先记录基线，再比较一项变化。低预算时先做不依赖真实模型的检索与来源验证。

如要增加一次真实模型实验，选择你愿意发送给提供方的合成样本，设定小规模调用计划，记录调用次数、模型名、实际 token 使用与失败。没有执行的真实模型实验标记“未验证”，不要用模拟结果代替。

**验收：**给出数据、计算方法和至少 3 个失败案例。解释测试验证的是确定的程序行为，评估回答的是一批样本上的质量，两者不能互相替代。

### 第 15 周 整理作品和简历

**本周问题：面试官怎样快速判断我到底做过什么？**

整理一个可运行的作品入口、一页简历、5 分钟演示和两个技术故事。README 需要写清项目用途、启动方式、你的实际贡献、测试与评估方法、已知限制。

至少一个故事来自你独立实现的内容，另一个来自你亲自复现并理解的问题。没有亲自修复的历史缺陷可以说“学习并复现了这个设计”，不能说“由我修复”。

**验收：**每条简历表述都能指出代码、记录或结果；遇到“这是你写的吗”能清楚说明 AI 辅助与自己的工作。不要在简历里放你解释不了的语言和框架清单。

### 第 16 周 模拟面试与投递

**本周问题：别人连续追问三次，我还能把项目讲清楚吗？**

进行两次 30–45 分钟模拟面试，一次以项目为主，一次以 Python、HTTP、SQL、数据结构和调试为主。把回答不清楚的问题归类，回到对应实验补证据。

筛选真实招聘信息，记录岗位职责、技术要求、地点、可到岗时间和实习时长。用你已完成的证据匹配岗位，不为了一个关键词临时宣称掌握整套框架。

**验收：**能完成 1 分钟介绍、5 分钟演示、15 分钟技术追问。第 12 周起如果已有独立成果且满足岗位要求，可以提前开始少量投递；不用等到每个选学技术都学完。

## 六 怎样读源码而不被几百个文件淹没

### 6.1 每次只追一个问题

建议按“使用说明 → 一条成功路径 → 一个错误分支 → 对应测试”的顺序读。第一次只画箭头，第二次理解函数，第三次才深入算法。

读一个函数时，写四行笔记就够：

```text
输入是什么：
它做了哪几件事：
输出或副作用是什么：
什么情况下会失败或提前退出：
```

遇到陌生函数，先看名称、参数、返回值和调用位置。只有影响当前问题时才继续展开，避免从聊天按钮一路读到所有底层库。

### 6.2 四条最重要的阅读路线

**路线 A 普通聊天：**`ChatInput.tsx → chat-runtime.ts → api.ts → commands/gateway.rs → gateway/handlers.go、stream.go → providers`。然后追返回事件如何写入消息状态、取消如何传递。普通聊天的上下文准备还会经过 knowledge 服务。

**路线 B 项目知识：**`CodeLensPage.tsx → Go CodeLens adapter → Python project_index.py → symbol_chunks.py → Nebula project.go → knowledge/service.go → 聊天引用展示`。索引是准备资料，检索是在回答前选择资料；这两个步骤要分开。

**路线 C 只读 Agent：**`chat-runtime.ts → agent-transport.ts → workspaces 任务入口 → agent/run.go → registry.go → gateway/tools.go → 工具结果与任务事件`。Agent 分支会把工作交给后台任务，不是普通聊天流外面多画一个标签。

**路线 D 可审批操作：**`Agent 提出操作 → actions.go 保存 → AgentActions.tsx 展示 → action_http.go 接收确认 → 文件操作或 action_executor.go 执行 → 保存结果 → 条件满足时恢复`。模型任务结束与操作执行结束是两回事。

这些是方便阅读的逻辑路线，并不表示每一箭头都是两个文件之间的一次直接函数调用。

## 七 做一项真正属于你的独立实践

前面的小实验用来学会概念，后面这项实践用来形成可以展示的个人贡献。不要同时做三个大功能。

### 7.1 推荐题目 代码检索与来源有效性评估工具

**要解决的问题：**现在项目有检索与来源检查能力，但仅仅点几次界面，很难知道一批问题上的命中情况，也难以稳定比较修改前后的结果。你可以独立写一个小型评估工具，生成可复查的结果。

建议范围为 20–30 个检索问题，使用你自己建立的 10–20 个源码文件。样本里包含普通问法、精确函数名、中文问法、相似函数名，以及少量项目中没有答案的问题。

工具分三步完成：

1. **先做离线评分器。** 读入问题标注和你保存的检索结果，计算指标并输出 JSON/CSV。此时不用处理桌面鉴权。
2. **再接结果收集。** 通过项目已有的鉴权上下文接口采集结果，或使用隔离测试夹具导出。使用临时工作区与临时凭证，不在脚本中写真实密钥。
3. **最后写分析报告。** 显示哪些问题成功、哪些失败、失败属于哪类，以及一个下一步改进方向。

先定义一个你能解释的样本格式：

```json
{
  "id": "q001",
  "query": "用户点取消后在哪里检查取消状态",
  "answerable": true,
  "relevant_units": ["src/runner.py::check_cancelled"],
  "project_version": "fixture-v1"
}
```

这里的文件与符号只是你未来创建的夹具示例，不表示 Noosphere 存在 `src/runner.py`。标注单位可以选文件或符号，但整次实验必须一致。一个文件包含多个相关片段时，按文件统计就先去重，不能靠重复片段虚增命中。

**必须由你独立完成的核心：**数据格式设计、读写逻辑、至少一个指标函数、异常处理、手工核对与报告解释。可以用 AI 帮忙审查，但你要能从空文件重写主要计算逻辑。

**交付证据：**一个可运行入口、标注样本、原始结果、指标表、失败案例、复现命令和自己的版本记录。

### 7.2 选择一项很小的产品改进作为进阶

评估工具完成后，再根据实际观察选一个问题。比如：某类检索失败提示没有说明下一步，或某个状态在界面里很难区分。

先复现，确认当前代码确实存在这个问题，再写出预期行为和验证方式。如果已经被解决，就换一个有证据的问题，不为“做新功能”重复实现现有能力。

优先选择一周内能完成的小范围改进，例如一个错误提示、一处结果展示或一个经样本验证的过滤规则。暂时不选“把整个项目迁移到另一个框架”“重写全部存储引擎”或“同时加入多 Agent 自动开发”。

有意义的测试应覆盖实际行为或边界。只有静态文字变化时不必为了数量新增测试；涉及状态、请求、过滤或数据处理时，补充能够检验行为的测试。

### 7.3 选学路线

如果你更喜欢后端，可以把独立实践换成一项已复现的任务状态问题，并补充测试；如果更喜欢代码理解，可以针对一个明确支持的语法边界改进切分并验证。选择应由你观察到的问题决定。

无论选择什么，必须能完成这条叙述：**我发现了什么 → 怎样复现 → 为什么发生 → 做了什么 → 怎样验证 → 还存在哪些限制。**

## 八 如何评估 检查与记录

### 8.1 先把三种质量分开

| 层次 | 要问的问题 | 适合的方法 |
|---|---|---|
| 程序行为 | 错误参数是否拒绝，取消是否生效 | 自动化测试与故障场景 |
| 检索质量 | 相关来源能否排进前 k 个结果 | 固定问题集、人工标注、排名指标 |
| 模型回答 | 结论是否正确，是否被来源支持 | 真实模型小样本、逐条人工复核 |

模拟模型很适合第一层；哈希向量模式的检索实验只代表该模式；第三层需要实际模型输出。报告必须明确自己验证到了哪一层。

### 8.2 初学阶段够用的指标

**Hit@k：**有答案的问题中，前 k 个结果至少包含一个相关单位的问题数，除以有答案的问题总数。例如 20 个问题中 15 个命中，Hit@5 为 75%。这个数字只是公式示例，不是本项目实测成绩。

**Recall@k：**对每个有答案问题，用前 k 个结果里的相关单位数除以人工标注的相关单位总数，再说明如何汇总。一个问题只有一个标注答案时，它和该题 Hit@k 的结果会一致。

**来源有效率：**实际提供给模型的代码引用中，项目归属、文件存在、版本哈希均符合要求的引用数，除以被检查的代码引用总数。没有引用时记为“不适用”，不能为了好看记作 100%。整理记忆要按自己的来源类型与状态规则另列检查。

**耗时：**记录每次耗时和中位数。样本很少时可以列原始值与范围，不急着用 p95 制造精确感。只测索引发布时就写“索引发布耗时”，不能写成“用户总等待时间”。

**Agent 任务成功率：**只有先为每个任务定义可检查的成功条件，才能计算成功任务数除以任务数。工具调用返回成功、模型答案声称成功，都不自动等于用户目标完成。

**调用成本：**优先记录请求次数、输入与输出 token。需要估算费用时再查当时实际提供方价格；本方案不写固定价格，也不假设所有服务的 token 统计方式完全相同。

无答案问题单独统计是否错误提供不相关依据、是否给出无依据结论，不把它们混入有答案问题的 Hit@k 分母。

### 8.3 推荐的一组小型实验

对固定代码夹具建立 24 个问题，其中 20 个可回答、4 个不可回答。这是建议起始规模，不是完成求职所需的硬性数量。

先手工核对 5 个问题的评分结果，再跑完整集。可回答问题按需要划分为开发集和保留评估集，例如 12 个用于调试、8 个用于最后报告；保留集不要随着每次改动反复挑选或重写答案。

第一轮只比较两种设置，例如“原设置”和“一项修改”。固定模型、向量模式、项目版本、问题、top-k、超时和机器环境。做 3 次运行观察波动；样本小，报告用于学习和定向诊断，不宣称能代表所有项目。

把来源过期、取消、权限和重启放在单独的行为验证表中，避免把安全行为和检索排名混成一个模糊的总分。

| 记录项 | 你需要填写的内容 |
|---|---|
| 日期与源码版本 | 有 Git 用提交号；尚无 Git 时记录快照名与关键文件哈希 |
| 测试环境 | 操作系统、关键运行时版本、机器配置 |
| 数据 | 文件数、问题数、标注规则、保留集划分 |
| 检索设置 | top-k、关键词/哈希向量/真实 embedding 模式 |
| 模型设置 | 无模型、模拟模型或真实模型；实际模型标识 |
| 原始结果 | 每个问题返回的来源、名次、耗时和错误 |
| 汇总结果 | 明确分母的指标、波动与失败案例 |
| 结论 | 哪项改善，哪项没有改善，哪些尚未验证 |

### 8.4 现有性能记录如何使用

项目知识文档记录过小样本索引发布和符号切分基准。可以学习它的测量方式，并亲自复跑适合当前环境的命令；不要把那里的历史数字直接写成“我优化后提升了多少”。

如果要写性能提升，需要同环境、同数据、相同测量范围的前后对照。没有旧版本或可靠基线时，只写当前测量结果，不计算不存在的提升比例。

若使用“耗时下降比例”，公式是 `(原耗时 - 新耗时) / 原耗时`。例如从 100 ms 到 80 ms，耗时下降 20%；“速度提升 25%”是另一个表述，初学报告优先使用前者，避免混淆。

## 九 怎么把项目写进简历

### 9.1 推荐的项目定位

项目名称可以用：**Noosphere 本地 AI 代码工作台**。

介绍方向可以用：**面向代码项目的检索问答、可追溯工具执行与人工审批**。

| 中级 | 模型怎么调用工具 | 结构化请求、校验、执行、调用 ID、结果回传 |
| 中级 | 点取消后发生什么 | 取消信号如何传递，迟到结果如何被处理 |
| 中级 | 怎么防止用到旧项目或旧代码 | 工作区绑定、命名空间、项目核对、源码哈希 |
| 进阶 | 增量索引省掉了什么工作 | 未变文件解析、未变片段向量、元数据更新、图重建范围 |
| 进阶 | 重复审批和恢复冲突怎么办 | 保存的操作 ID、状态、原/新哈希、拒绝覆盖 |
| 进阶 | 你怎样知道改进有效 | 固定样本、基线、指标、失败案例与验证边界 |

每题按“具体例子 → 实际设计 → 为什么 → 限制”回答。答不清楚时回到实验补充理解，不必靠背更长的答案解决。

### 10.3 三个特别值得练熟的技术故事

**故事一 为什么有引用也可能回答错。** 先区分检索没找到、来源过期、引用只支持部分结论、模型没有遵循来源。说明项目的来源校验解决了哪部分，你的评估还检查了哪部分。

**故事二 为什么恢复不能直接写回旧文件。** 先举用户在外部编辑器修改文件的例子，再解释 before/after 哈希检查。说明这是有条件的单项恢复，不是多文件事务，也没有消除所有并发写入竞态。

**故事三 为什么程序重启后不自动继续执行。** 解释进程可能在“动作发生后、结果保存前”退出，系统无法仅靠旧状态就确认是否该再执行。当前选择标记中断并要求核查，是对重复副作用的控制。

这些设计已经在项目里存在。面试时明确哪些是你阅读理解的，哪些是亲自复现或改进的。

### 10.4 基础能力不能被项目包装替代

每周保留约 2 小时，按顺序练：

1. 第 1–4 周：字符串、列表、字典、集合、函数、文件、异常。
2. 第 5–8 周：时间复杂度直觉、栈和队列、排序与二分、HTTP、进程与线程基本区别。
3. 第 9–12 周：SQL 查询、主键、索引基本用途、事务、锁、并发与取消。
4. 第 13–16 周：按实际面试反馈补题，练习边写边解释和定位错误。

每周做 2–3 个你能完整解释的小题，比只抄很多答案更有用。比如去重、词频统计、括号匹配、二分查找；完成后自己说明输入边界和复杂度。不把题目数量当作能力本身。

## 十三 开发与验证命令手册

以下是你后续练习时使用的命令，来自当前项目脚本与配置。本次只核对入口，没有重新执行这些构建和测试，因此这里不宣称当前环境运行全部通过。

### 13.1 路径和环境

先在 PowerShell 中进入项目根目录：

```powershell
Set-Location -LiteralPath 'E:\project\Noosphere（agent项目）\new'
```

只读预检会检查工具和依赖，不会替你安装，也不代表编译和运行验收：

```powershell
powershell -NoProfile -File .\scripts\preflight.ps1 -RequireDesktop
```

项目开发指南目前要求 Go 跟随 `backend/go.mod` 的 1.26.5，Python 3.10 以上，Rust 1.88 以上；前端测试使用 Node 24。具体以当前开发指南、锁文件和预检结果为准。先确认现有环境，不必全部卸载重装。

缺少前端依赖时再按开发指南执行：

```powershell
npm --prefix frontend ci
npm --prefix desktop ci
```

`ci` 使用锁文件安装依赖；不要一遇到报错就删除锁文件或改版本。

### 13.2 小范围测试优先

Go 命令需要 Go 已在当前终端 PATH 中；如果预检通过而终端找不到 Go，先查看 `scripts/common.ps1` 的本地工具回退，不要把“找不到命令”误判成业务代码失败。

```powershell
Push-Location .\backend
try {
    go test ./internal/agent -run TestLoopUsesStructuredResultsAndStopsRepeatedFailure -count=1
} finally {
    Pop-Location
}
```

这是指定一个测试。读懂后再运行相关包，最后在改动影响多个模块时运行全套：

```powershell
Push-Location .\backend
try {
    go test ./...
    go vet ./...
} finally {
    Pop-Location
}
```

前端测试与构建：

```powershell
npm --prefix frontend test
npm --prefix frontend run build
```

使用项目现有 Python 虚拟环境运行测试，前提是该解释器和测试依赖已安装：

```powershell
Push-Location .\backend\python\codelens
try {
    & '..\..\..\.local\venv\Scripts\python.exe' -m unittest discover -v
} finally {
    Pop-Location
}
```

Rust 测试属于后期验证，前期不必每天全量执行：

```powershell
cargo test --lib --locked --manifest-path .\desktop\src-tauri\Cargo.toml
```

退出码、失败日志与实际断言都要看，不能仅凭屏幕最后出现“完成”就认为测试通过。

### 13.3 运行与构建要分清

打开已有程序，使用根目录的 `Start-Noosphere.cmd`。源码开发按指南使用：

```powershell
powershell -NoProfile -File .\scripts\dev.ps1
```

只更新开发用后端与前端产物：

```powershell
powershell -NoProfile -File .\scripts\build.ps1 -SkipTauri
```

完整构建会更新发布产物，不是每次改一行都必须执行的学习动作。独立后端启动涉及本地凭证，按开发指南现有流程操作；不要为图方便移除认证。

Agent 内置“运行测试”提案的固定 runner，和你在终端执行项目专用 npm/Go 测试命令，不是同一个入口。解释清楚工作目录和 runner 是否匹配，再判断结果。

### 13.4 报错时按这个顺序检查

1. 命令是否在正确目录执行，目标文件是否存在。
2. 错误发生在工具找不到、依赖安装、编译、运行还是测试断言阶段。
3. 阅读第一个有意义的错误和相关调用栈，不只看最后一句。
4. 缩小到一个函数、一个接口或一个测试，稳定复现。
5. 写出你的原因猜测，再用日志或小实验检查。
6. 只改一个原因相关的地方，复跑对应验证，再检查影响范围。

把“症状、输入、原因、改动、证据”记下来。这些记录会比零散截图更适合整理成面试故事。
