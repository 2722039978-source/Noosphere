# 会话全文搜索与优化方案

## 本次交付

现有 AI 对话保存在本机，但历史侧栏只能按时间逐条查找。本次补充标题和消息正文搜索，在结果中展示关键词及上下文，点击正文命中后打开会话、滚动到对应消息并高亮。浏览命中时暂停自动滚底，点击“返回最新消息”或发送新消息恢复。

使用入口：AI 对话 → 左侧“搜索会话”；窄屏点击顶部“AI 对话”打开会话历史。输入即搜索，清空按钮或输入框中的 Esc 恢复完整列表。窄屏 Esc 在查询非空时先清空，再次按下才关闭面板。

规则与边界：

- 检索本机 `noosphere-chat-v1` 中的会话标题、用户消息和助手消息，不调用模型或 Nebula。
- 去除查询首尾空白，按字面子串匹配且忽略大小写；内部空格保留，特殊字符不按正则解释。
- 每个会话展示一个结果：优先命中标题，否则展示按消息顺序找到的第一条正文命中。结果按最近更新时间排列；相同时间保持原顺序。
- 片段保留原文大小写与 Unicode 字符，高亮通过 React 文本节点渲染。标题前置上下文最多 3 个码点，正文最多 8 个，保证窄侧栏先显示命中位置。
- 搜索不改变会话内容或本地存储结构。关键词、缓存与定位状态均不持久化；删除或重新生成移除目标后，定位自动失效。
- 当前不支持模糊搜索、拼音、同义词、附件独立全文或一个会话内多个命中的逐个导航。点击长消息会定位消息顶部或中央，不定位 Markdown 内部的具体词。

## 已实施的优化

| 优化 | 实现 | 作用与限制 |
| --- | --- | --- |
| 隔离输入与结果渲染 | `SessionSidebar.tsx` 的 `useDeferredValue`、独立 `memo` 结果列表和条目 | 优先响应输入，结果使用同一延迟关键词；首次大规模扫描仍发生在主线程 |
| 按不可变对象复用搜索结果 | `session-search.ts` 使用会话与消息两层 `WeakMap` | 相同关键词下，未变化会话直接复用；流式 token 更新仅使被替换对象失效 |
| 复用小写文本 | 消息首次参与搜索时建立内存缓存，每项只留最近一次查询结果 | 避免每次都把全部历史转为小写；内存有额外文本开销，删除对象可随 GC 回收 |
| 空搜索跳过正文 | 直接列出会话元数据 | 平常浏览历史不建立全文缓存 |
| 延迟加载后的可靠定位 | `MessageBubble.tsx` 在挂载后响应带序号的定位请求 | 首次懒加载和重复点击同一结果均可定位，仅滚动消息容器 |
| 定位期间保持阅读位置 | `ChatPage.tsx` 校验会话 ID、消息 ID 并暂停自动滚底 | 新 token 不打断查看旧消息；支持显式返回最新消息 |

设历史总字符数为 C、会话数为 S：新关键词最坏仍需扫描 C 并排序结果；同关键词下历史未变时，工作主要是遍历会话和排序，避免重复扫描全文。缓存依赖 store 现有的不可变更新方式，后续不得原地修改消息对象。

## 合成数据性能测量

2026-09-08，Windows x64 / Node v24.19.0：1,000 会话 × 20 消息 × 200 字符，正文共 4,000,000 字符、标题共 6,890 字符。每个会话只在最后一条消息命中，所有检索结果 ID 均与简单全扫描基线一致。

| 测量 | 本机耗时 |
| --- | ---: |
| 首次检索并建立缓存 | 18.714 ms |
| 相同关键词连续 30 次中位数 | 0.133 ms |
| 一个会话的末条消息追加字符后检索 | 0.279 ms |
| 简单全文扫描连续 30 次中位数 | 8.590 ms |

缓存主要改善重复检索和流式更新；首次建立缓存耗时高于基线。基线只扫描、排序，不生成摘要。以上是一次 Node 合成数据运行的函数耗时，不包含 React、DOM、存储、GC 压力等实际界面成本，不能视为 UI 延迟或其他设备的性能保证。

## 后续优化优先级

2026-09-09 更新：两项 P1 已实施，详见 [界面与流式稳定性记录](RHINE_UI_STREAMING.md)。P2 / P3 仍为后续建议；验收指标为目标，不是本次测量结论。

| 优先级 | 现状依据 | 建议与验收 |
| --- | --- | --- |
| P1：减少流式写盘（已完成） | 原来每个 token 都序列化全部会话 | 现在按 32ms 合并显示，按 250ms 合并序列化和保存；完成、取消、页面隐藏和正常关闭时立即保存，失败可重试 |
| P1：让停止按钮终止请求（已完成） | 原停止按钮只阻止显示 token | 现在通过独立请求 ID 取消 Tauri HTTP future，触发 Go 上下文取消；测试覆盖首包前取消、旧回调隔离和连接实际关闭 |
| P2：规模化全文搜索 | 当前搜索在主线程扫描，历史由 localStorage 保存 | 先在目标设备记录输入到结果绘制的 p50/p95、存储大小和首次检索耗时；如约 1,000 会话测试下 p95 超过 100ms，再引入 Worker。更大历史迁移 IndexedDB 或本地 SQLite，并提供版本迁移和失败恢复 |
| P2：长列表渲染 | 结果列表及当前会话消息仍整体渲染 | 在大结果集产生可见卡顿时引入虚拟列表；保留键盘焦点和“按消息 ID 定位”的接口，覆盖未挂载消息定位和窗口缩放 |
| P3：细化检索体验 | 每会话只显示第一个命中 | 增加会话内上一个/下一个命中、日期与模型筛选；保持筛选状态可解释，再考虑模糊检索或语义召回 |

后续根据实际历史规模决定是否需要 Worker、数据库索引和虚拟列表。
